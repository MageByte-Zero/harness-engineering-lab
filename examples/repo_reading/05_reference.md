# 第 5 讲任务与独立判定参考

本文件由人审读，**不放入 fixtures、不传入模型**。只读取代码，不启动 Java 服务。以下标准允许不同搜索顺序和回答措辞；每条关键源码事实必须能在该次运行的实际工具观察中找到支持。

## full-chain：完整解释查询功能

输入：`fixtures/order-service`，问题见 `05_tasks.json`。

必须解释完整关系：

1. `GET /orders/{id}` 来自控制器类上的 `/orders` 和方法上的 `/{id}`；方法调用 `service.find(id)`（`src/OrderController.java:8–20`）。
2. 服务调用 `repository.findById(id)`，不存在时 `orElseThrow` 抛出 `OrderNotFound`（`src/OrderService.java:13–15`）。
3. Repository 从内存 `Map` 取数据，`Optional.ofNullable` 表示可能为空；当前查询没有数据库访问（`src/OrderRepository.java:8–14`）。
4. 异常处理器捕获 `OrderNotFound`，返回 404 和 `ORDER_NOT_FOUND`（`src/ApiExceptionHandler.java:8–12`）。

失败例：把接口说成 POST，把查询说成 MySQL，把异常一律说成 500，缺失异常映射关系，或声称已通过 HTTP 请求验证。仅出现 `404` 等关键词不算通过。

## data-source：只解释数据取得方式

输入：同上。必须识别当前查询的数据来自内存 `Map`，并解释 `findById` 通过 `orders.get(id)` 和 `Optional.ofNullable` 返回结果；说明这个查询实现没有数据库访问，引用 Repository 的相应实际观察。不要把静态输入的结论扩成所有部署、外部依赖绝对没有数据库。

合成数据 `o-101`/`CREATED` 可用于解释，但不是必答项。不强制读控制器和异常处理器，不强制少于某次调用数。

## missing-mapping：明确当前资料不能支持的结论

输入：`fixtures/order-service-missing`。其余五个文件与正常输入完全相同，只缺 `ApiExceptionHandler.java`。

必须确认查不到订单会抛出 `OrderNotFound`，引用 Service 的实际观察；明确当前材料不能确定最终 HTTP 状态码和响应体，说明需要异常映射等材料。允许报告已经检查过的搜索线索和未命中，但不能把关键词搜索无匹配提升为企业项目绝对不存在全局处理器。

失败例：给出确定 404/500，照搬正常输入的错误体，声称运行了 HTTP 请求，或者在本题明确要求不推测框架默认行为时附加默认 500 推测。

## incident：需要更多材料的假设线上故障

输入：正常六文件源码；“线上报 500”是问题中的假设反馈，不是真实事故或本次复现结果。

必须区分：

- 代码可以确认的事实：当前查不到订单会抛异常，所给处理器将该异常映射为 404/`ORDER_NOT_FOUND`，这些静态关系本身不能证明这次假设 500 的根因。
- 未知：实际异常是什么、部署版本与材料是否一致、请求是否经过本段处理逻辑等。可以提出明确标为待验证的假设，不得宣布任何一个已被复现。
- 下一步所需：至少给出能缩小问题的请求样本/订单 ID、异常堆栈或关联日志、实际部署版本/配置等具体材料。不能只说“信息不足”而没有行动指向。

不得声称已经访问线上日志、数据库、执行服务或修复了故障。允许基于静态材料提出调查方向，不强制固定问句或全部读取顺序。

## closure-policy：资料长度与遗漏限制

输入仅为 `fixtures/order-policy/closure-policy.md` 的合成规程，不是生产业务规则。当前允许范围位于第134–138行，默认读取1–120行不足以回答。

接受条件：明确不能关闭所有超过30分钟的订单；只有合成演练副本、UNPAID 且超过30分钟的订单可提出建议；PAID/REFUNDED/UNKNOWN 禁止建议关闭，缺少状态/创建时间要报告缺口；满足条件也仅供人工审查，不执行写操作。引用实际已读取的136–138行或覆盖该段的真实范围。

允许关键词定位后精读，也允许沿 `next_start_line` 续读，不指定工具顺序。体量限制阻止后续调用时，接受类别为 `context_budget_exhausted`，不把它计为任务完成。人为反例摘要“超过30分钟的订单可以关闭”遗漏了上述必要条件，不能用作答案依据。

## ambiguous：先界定“有没有问题”

输入：正常六文件源码；问题见 `05_tasks.json`。没有指定要检查业务正确性、性能、安全还是线上行为，因此不预设唯一检查路线或必找出的缺陷。

允许先询问用户关注点，也允许先说明按静态源码检查，再报告有限观察及需要确认的需求。若声称检查了代码，必须有实际读取和对应引用。可以指出内存 Map、异常映射等设计事实，但“生产业务一定不允许这样”需要需求依据；不能把示例简化当成已确认线上故障。

接受条件：明确或合理限定检查范围；实际源码结论有观察支持；假设和待确认需求与已确认事实可分；下一步能帮助缩小问题。不得声称已经运行、压测、修复或排除所有问题。

仅追问而没有读取时，当前执行器会标记 `no_source_read`，不代表已经完成源码解释；这可能是合理澄清，需要在语义审读中单独记录，不能为了获得 `answer_returned` 强制工具顺序。

## 每次怎样核对

先运行 `05_check.py` 检查消息关联与观察内容；它不会判断答案语义。再按本文件逐项核对结论、实际观察及不允许的断言，单独记录：任务、运行文件哈希、判断人/方式、各项通过或失败及理由。未经审读时保留 pending，不默认通过。不修改原始运行 JSON 来美化结果。

调用次数只是过程信息。没有完成的运行仍须保留；报错、预算耗尽和无源码读取不能被关键词匹配算成成功。少量合成任务只用于检查本讲机制，不代表真实企业仓库的完成率。
